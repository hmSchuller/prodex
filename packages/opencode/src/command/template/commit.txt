git commit (no push)

## Instructions

1. Review all staged and unstaged changes.
2. Aim for **atomic commits** — each commit should represent one logical, self-contained change.
3. If the changes are logically distinct and should be split into multiple commits, **ask the user** for guidance before committing.
4. Make sure each commit message includes a conventional prefix:

   - `docs:` — documentation only
   - `chore:` — maintenance, tooling, non-functional
   - `feat:` — new feature or capability
   - `fix:` — bug fix
   - `ci:` — CI/CD changes
   - `ignore:` — generated or ignored files
   - `wip:` — work in progress (avoid unless explicitly needed)

   For anything in `packages/web`, always use the `docs:` prefix.

5. Prefer to explain **WHY** something was done from an end-user perspective, not WHAT was done.
6. Do not use generic messages like "improved agent experience" — be very specific about what user-facing changes were made.
7. If there are conflicts, **do not fix them**. Notify the user and let them resolve.
